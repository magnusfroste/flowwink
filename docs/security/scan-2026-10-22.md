# Security scan — 2026-10-22

**Scope:** the whole FlowWink CMS as deployed from `main` (910c5f3): 79 edge
functions (55 public), 402 tables with RLS, ~340 SECURITY DEFINER functions, the
React frontend (public blocks, admin, chat, mail), dependencies, HTTP headers, and
two live instances (sandbox, www) probed read-only with the anon key plus
authorised write probes on sandbox (test accounts deleted afterwards).

**Method:** `npm audit`; a static read of every public edge function's caller
gate; a replay of all 671 migrations for the effective RLS policies, grants and
definer bodies; a read of every `dangerouslySetInnerHTML` and content-derived
`href`; and live probes: anon PostgREST reads of 34 tables, anon inserts into 13,
anon RPC on 12 definer functions, GoTrue signup with crafted metadata, and the
response headers of www and sandbox.

## Findings

| # | Severity | Finding | Fix |

No abuse found (www: one admin, created 2026-08-11 by provisioning). | Migration `20261022010000`: the request is read from `raw_app_meta_data`, which only the service role can write; `create-user`, `customer-signup`, `flowwink.sh` and the view-sweep fixtures send `app_metadata`. Verified on sandbox. | Same migration: 72 internal tables now `is_staff(auth.uid())`; `profiles` is own row or staff. Reference tables (currencies, units, tax codes, public catalogue) stay open. **Known and ratcheted before this scan:** 21 public edge functions with no
caller check (`KNOWN_UNGATED` in `public-functions-verify-their-caller`), among
them the paid agent tools (web-scrape, browser-fetch, web-search, extract-pdf-text,
process-image) and the cron entry points. Unchanged by this sweep; the ratchet
may only shrink.

## What held

- RLS is on for all 402 tables; anon reads exactly the public content (pages,
  posts, catalogue, settings allowlist — `integrations` excluded) and nothing
  else; anon inserts are limited to forms, bookings, page views, UTM.
- Webhook signatures: Stripe, Telegram (secret token), Composio (HMAC when the
  secret is set) verified; the anon cron caller of `composio-proxy` is pinned to
  one read-only action.
- The service key reaches no frontend bundle; no credential in the tracked tree
  (one stale anon key of a dead project aside); cron commands carry no service key.
- Admin routes gate on roles before rendering; the Supabase session is the only
  token in storage.

## Live verification after merge

401; customer JWT on `employees` → 0 rows; `register_visitor_intent_trigger` as

`fleet-check-signup-escalation.sql` and are rerun on www after `db push`.

## Fleet state — 2026-10-24

Reconciled by the local session two days after the sweep. The order was: the
storage SQL by hand on seven instances the night of the 22nd, the hotfix on the
five forks still vulnerable, and the nightly fork sync (01:23 UTC) carrying
migration `20261022010000` to every instance. The probe below is a READ after
the sync — the end state, not an exit code.

Nine instances reachable: www, sandbox, nordbrygg, autoversio, liteit, optic,
resta, mjpdemos (the labs1100 ref) and synclair.

| Check | Result |
|---|---|
| Migration `20261022010000` | applied on all nine |
| `handle_new_user` reads `user_metadata` | no, on all nine |
| Storage policies staff-only, 5 of 5 | yes, on all nine |
| Admin and writer accounts | only known owners and provisioned agents; no account with a role nobody granted |
| 46elks, Twilio, GatewayAPI | no instance has a provider configured — no telephony edge secrets, no integration keys, no registered numbers. Re-saving the 46elks URLs (#726) is nothing to do until someone connects telephony; the secret is generated at save time. |

Three refs answer "tenant not found" and are gone or paused: the old liteit
(Ireland), demo (`ydcrzg…`) and the old labs1100 (`kpjzz…`, which the API still
lists but the pooler does not). Strike them from the next probe list.

**Open, by decision:** `disable_signup=true` in Supabase Auth is on only on
optic. Since the trigger now makes a self-registration a `customer`, this is
hygiene, not a hole — but free hygiene: every staff path (`customer-signup`,
`invite-colleague`, `invite-employee`, `create-user`) goes through
`auth.admin.*`, which the flag does not touch; the only thing it closes is
`supabase.auth.signUp()` from `AuthPage`, a door that now opens onto a
customer account nobody asked for. Recommended on for every instance:
Authentication → Sign In / Up → "Allow new users to sign up" off, or
`PATCH /v1/projects/{ref}/config/auth {"disable_signup": true}`.

## How to rerun this scan

```bash
npm audit --omit=dev --audit-level=high        # dependencies
npx vitest run src/lib/__tests__/*guardrails*   # every security guard, incl. the four from this sweep
```
Live: the anon-read probe, the signup probe and the policy inventory used here
are plain PostgREST/GoTrue calls and `pg_policies` queries; `.github/workflows/security-scan.yml`
(PR *security-hygiene*) runs the first two weekly and fails on a new critical.
